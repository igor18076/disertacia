# Техническое задание
## Разработка экспериментальной системы генерации учебного контента на основе гибридной архитектуры с контролем достоверности

**Кодовое название:** CourseGen Research  
**Версия ТЗ:** 1.0  
**Назначение:** научно-исследовательский прототип  
**Язык интерфейса и документации:** русский  
**Язык программирования:** Python  
**Тип приложения:** контейнеризированная система с REST API, CLI и экспериментальным модулем

---

# 1. Контекст и назначение проекта

Необходимо разработать программный комплекс для автоматизированного формирования учебных материалов на основе проверяемых источников знаний и формализованных требований образовательных документов.

Система предназначена для экспериментального исследования архитектур генерации учебного контента с использованием больших языковых моделей.

Принципиальное требование: LLM не должна самостоятельно определять содержание дисциплины, формировать требования или выступать единственным механизмом проверки собственной генерации.

Ответственность должна быть разделена следующим образом:

- Детерминированные алгоритмы обеспечивают контроль требований, планирование, выбор источников, проверку структуры и вычисление измеримых показателей.
- Поисковая подсистема извлекает подтверждающие фрагменты источников.
- Граф понятий описывает тематические и логические связи.
- LLM выполняет генерацию и изложение учебного материала в рамках переданных ограничений и доказательной базы.
- Независимая подсистема проверяет результаты, фиксирует ошибки и формирует отчёт.

Разработка выполняется в исследовательских целях. Система должна поддерживать воспроизводимые эксперименты и сравнение нескольких архитектур.

# 2. Цель исследования

Разработать и экспериментально оценить архитектуру генерации учебных материалов, основанную на совместном использовании гибридного поиска, графа понятий, формальных образовательных ограничений и ограниченного LLM-синтеза.

Проверяемая гипотеза:

Применение гибридного поиска совместно с графом понятий и алгоритмическим контролем требований позволяет повысить достоверность и соответствие учебных материалов образовательной программе по сравнению со свободной LLM-генерацией и традиционным RAG.

Гипотеза не должна считаться подтверждённой до завершения экспериментов и анализа результатов.

## 3.1. Ограничения развёртывания

Запрещается без отдельного разрешения:

- изменять существующие сетевые правила сервера;
- устанавливать сторонние сервисы напрямую в основную ОС;

Допускается использование предварительно согласованного Docker Engine и Docker Compose.

Если контейнерный runtime отсутствует, Codex должен сформировать инструкции по его установке, но не выполнять автоматически системные изменения.

Рабочий каталог проекта: `/opt/coursegen`, если его использование разрешено.

Все данные, базы, модели и результаты должны размещаться в выделенных томах или каталогах проекта.

## 3.2. Ресурсные ограничения

В конфигурации должны задаваться лимиты CPU и RAM для отдельных контейнеров.

Начальные ориентиры:

# 4. Технологический стек

## 4.1. Backend

- Python 3.12 или совместимая проверенная версия.
- FastAPI.
- Pydantic.
- SQLAlchemy и Alembic.
- PostgreSQL.
- Qdrant и официальный Python SDK.
- NetworkX.
- PyMuPDF для извлечения текста из PDF.
- pytest для тестирования.

Использовать типизацию Python и структурированное логирование.

При выборе PDF-библиотек учитывать условия лицензирования.

## 4.2. Поисковая подсистема

Основной поисковый движок: Qdrant.

Необходимо реализовать:

1. Лексический поиск BM25.
2. Семантический dense-поиск.
3. Гибридный поиск с Reciprocal Rank Fusion.
4. Поиск с учётом графа понятий.
5. Фильтрацию результатов по метаданным.

Использовать документированный механизм BM25 и гибридного поиска Qdrant для выбранной версии.

Если выбранный SDK не поддерживает необходимые возможности, сначала установить совместимую версию либо реализовать корректный адаптер. Нельзя незаметно подменять BM25 простым поиском по подстроке.

## 4.3. Языковые модели

Реализовать интерфейс `LLMProvider`.

Обязательные адаптеры:

- `DeepSeekProvider` — через официальный API.
- `OpenAICompatibleProvider` — для локального llama.cpp или другого совместимого сервера.
- `MockLLMProvider` — для тестов без сетевого доступа.

Выбор провайдера, название модели, endpoint, температура, лимит токенов и timeout должны задаваться конфигурацией.

Система должна запускаться без GPU.

Локальную LLM реализовать как дополнительный профиль Docker Compose. Основной pipeline не должен требовать обязательной загрузки большой модели.

API-ключи хранить в `.env`, не включать в Git, логи или результаты экспериментов.

## 4.4. Embedding-модель

Реализовать интерфейс `EmbeddingProvider`.

Требования к модели:

- возможность выполнения на CPU;
- поддержка русского языка;
- приемлемая работа с англоязычной технической терминологией;
- локальное вычисление embeddings;
- воспроизводимое версионирование модели.

Конкретную модель выбрать после технической проверки лицензии, доступности весов и CPU-производительности.

В конфигурации фиксировать идентификатор и ревизию модели, размерность вектора, способ нормализации и правила формирования входного текста.

Нельзя автоматически менять embedding-модель для существующей коллекции без переиндексации.

# 5. Модуль загрузки образовательных документов

Система должна поддерживать следующие источники:

- Рабочая программа дисциплины (РП).
- Фонд оценочных средств (ФОС).
- Учебники в PDF.
- Методические пособия.
- Документация в Markdown и TXT.

На первом этапе поддержка PDF, TXT и Markdown обязательна.

## 5.1. Обработка РП и ФОС

Необходимо извлекать и сохранять:

- наименование дисциплины;
- разделы и темы;
- компетенции и результаты обучения;
- виды учебных занятий;
- требования к содержанию;
- ограничения по объёму;
- требования к практическим работам;
- критерии оценивания.

Структура документов может отличаться, поэтому требуется разделить автоматическое извлечение, нормализацию и подтверждение данных.

Для каждого требования сохранять:

- уникальный идентификатор;
- тип;
- текст требования;
- исходный документ;
- номер страницы или другой указатель положения;
- статус подтверждения;
- версию документа.

При неоднозначном извлечении значение должно иметь статус `needs_review`.

Запрещается считать предположения LLM подтверждёнными требованиями.

Генерация материалов должна использовать утверждённый набор требований. Неподтверждённые элементы допускаются только в явно обозначенном исследовательском режиме.

## 5.2. Обработка учебной литературы

Этапы:

1. Регистрация документа.
2. Проверка типа и размера.
3. Вычисление SHA-256.
4. Извлечение текста.
5. Определение страниц.
6. Нормализация текста.
7. Выявление заголовков и разделов.
8. Разбиение на фрагменты.
9. Сохранение метаданных.
10. Построение индексов.

Необходимо сохранять исходный PDF.

Для каждого фрагмента хранить:

- `chunk_id`;
- `document_id`;
- `document_version`;
- `page_start`;
- `page_end`;
- `section_path`;
- `text`;
- `content_hash`;
- `token_count`;
- `language`;
- `extraction_status`;
- `embedding_model_version`.

По возможности дополнительно сохранять координаты текстовых блоков на странице.

В случае сканированного PDF без текстового слоя необходимо фиксировать необходимость OCR. OCR не должен выполняться незаметно или возвращать пустой текст как успешно обработанный документ.

Кодовые примеры, таблицы и формулы требуют отдельного контроля качества извлечения.

## 5.3. Актуальность источников

Источники должны иметь атрибуты:

- год издания;
- версию технологии;
- дату добавления;
- тип;
- статус актуальности;
- лицензионные ограничения.

Для устаревших учебников предусмотреть статус `historical` или `requires_verification`.

Например, учебник C# 2019 года допускается использовать для эксперимента, однако утверждения о современных версиях .NET и C# нельзя автоматически считать актуальными.

# 6. Разбиение документов на фрагменты

Реализовать несколько стратегий:

- разбиение по фиксированному количеству токенов;
- разбиение по заголовкам и смысловым разделам;
- иерархическое разбиение.

Размер фрагментов и перекрытие должны задаваться в конфигурации.

Начальные экспериментальные параметры:

- 400 токенов;
- 800 токенов;
- 1200 токенов;
- перекрытие 10–15%.

Параметры рассматриваются как исследовательские, а не заранее оптимальные.

Обязательно сохранять связь фрагмента с исходным документом и страницами.

Для каждого фрагмента должны существовать методы восстановления источника и проверки, что извлечённый текст действительно присутствует в зарегистрированной версии документа.

## 7.2. Qdrant

Использовать для поиска по учебным фрагментам.

Предусмотреть именованные представления или соответствующие конфигурации для:

- dense-поиска;
- BM25-поиска;
- гибридного поиска.

В payload необходимо хранить необходимые для фильтрации идентификаторы и метаданные.

Не дублировать без необходимости всю реляционную модель PostgreSQL.

Предусмотреть:

- создание коллекции;
- проверку схемы;
- пакетную индексацию;
- обновление документа;
- удаление документа и его фрагментов;
- повторную индексацию;
- диагностику расхождений между PostgreSQL и Qdrant.

Операции переиндексации должны быть идемпотентными.

Система должна обнаруживать неполную индексацию и обеспечивать повторное выполнение без создания дубликатов.

# 8. Модуль гибридного поиска

Реализовать общий интерфейс:

```python
class Retriever(Protocol):
    def search(
        self,
        query: str,
        filters: RetrievalFilters,
        top_k: int
    ) -> list[RetrievedChunk]:
        ...
```

Обязательные режимы:

- `bm25`;
- `dense`;
- `hybrid`;
- `hybrid_graph`.

При гибридном поиске использовать RRF как базовый метод объединения.

Количество кандидатов от каждого поискового механизма должно настраиваться отдельно от итогового `top_k`.

Результат поиска должен содержать:

- идентификатор фрагмента;
- идентификатор документа;
- текст;
- страницы;
- доступные оценки релевантности;
- итоговый ранг;
- тип использованного поиска;
- сведения о применённых фильтрах.

Нельзя напрямую складывать BM25 и cosine similarity без корректной нормализации.

Предусмотреть фильтрацию по типу источника, актуальности, теме, версии документа и разрешённому корпусу.

# 9. Граф понятий

Граф должен представлять учебную дисциплину в виде связанных понятий.

Начальная реализация — NetworkX.

Типы узлов:

- учебная тема;
- понятие;
- результат обучения;
- компетенция;
- источник;
- фрагмент источника.

Типы связей:

- `prerequisite_of`;
- `part_of`;
- `related_to`;
- `covers`;
- `supported_by`.

Каждая связь должна иметь происхождение:

- извлечена из документа;
- создана правилом;
- предложена LLM;
- подтверждена экспертом.

Предложения LLM нельзя автоматически считать достоверными связями.

Для графа реализовать:

- создание;
- редактирование;
- версионирование;
- проверку связей;
- поиск пререквизитов;
- определение недостающих понятий;
- фильтрацию и расширение поисковых запросов.

Система должна обнаруживать циклы в связях пререквизитов и сообщать о них.

Граф должен влиять на планирование или поиск измеримым образом. Простое отображение графа без использования в алгоритме не считается реализацией этого модуля.

# 10. Алгоритмическое формирование учебного содержания

Общий pipeline:

1. Получение запроса на создание материала.
2. Определение темы и типа материала.
3. Выбор утверждённых требований РП и ФОС.
4. Построение обязательного плана.
5. Определение требуемых понятий.
6. Поиск подтверждающих фрагментов.
7. Анализ покрытия понятий и требований.
8. Проверка достаточности найденной базы знаний.
9. Формирование ограниченного контекста.
10. Вызов LLM.
11. Структурная и фактическая проверка результата.
12. Сохранение материала и отчёта.

## 10.1. Критерий достаточности доказательной базы

Ввести настраиваемый составной показатель:

\[
S = w_1C + w_2R + w_3A + w_4D
\]

где:

- \(C\) — доля обязательных понятий, покрытых источниками;
- \(R\) — оценка релевантности подтверждающих фрагментов;
- \(A\) — доля источников, удовлетворяющих требованиям актуальности;
- \(D\) — оценка разнообразия и независимости подтверждений;
- \(w_i\) — веса, сумма которых равна 1.

Это начальная исследовательская формализация, а не доказанная метрика достоверности.

Метод расчёта каждой составляющей, нормализацию и веса необходимо документировать.

Порог \(S_{\min}\) задаётся конфигурацией и калибруется на размеченных примерах.

Дополнительно установить обязательные ограничения, которые нельзя компенсировать высоким суммарным баллом:

- покрытие критических понятий;
- отсутствие неподтверждённых обязательных требований;
- наличие проверяемых источников;
- соблюдение ограничений допустимого корпуса.

Если доказательной базы недостаточно, система должна возвращать статус `insufficient_evidence` и перечень пробелов, а не генерировать уверенный текст из предположений.

# 11. Генерация учебного контента

Поддерживаемые типы материалов:

- лекция;
- конспект;
- практическое задание;
- лабораторная работа;
- контрольные вопросы;
- тестовые задания.

В первом MVP достаточно полностью реализовать лекцию и практическое задание.

Генерация должна происходить по заранее подготовленной структуре.

LLM получает:

- утверждённый план;
- обязательные понятия;
- проверенные извлечённые фрагменты;
- идентификаторы источников;
- ограничения РП и ФОС;
- правила оформления;
- запрет на выдумывание источников и ссылок.

Генерация должна поддерживать структурированный результат JSON, проверяемый Pydantic.

Предусмотреть отдельные статусы:

- `draft`;
- `generated`;
- `validation_failed`;
- `needs_review`;
- `approved`.

Каждое существенное фактическое утверждение должно быть связано с одним или несколькими идентификаторами доказательных фрагментов.

Указание существующего идентификатора само по себе не доказывает, что источник подтверждает утверждение.

# 12. Подсистема независимой проверки

Необходимо реализовать несколько независимых уровней контроля.

## 12.1. Структурная проверка

Проверять:

- наличие обязательных разделов;
- соответствие формату;
- допустимый объём;
- покрытие обязательных тем;
- наличие требуемых элементов задания;
- соответствие утверждённым ограничениям.

Проверку выполнять детерминированными алгоритмами.

## 12.2. Проверка источников

Проверять:

- существование указанных идентификаторов;
- соответствие идентификаторов использованному корпусу;
- наличие исходных страниц;
- отсутствие ссылок на удалённые версии документов;
- корректность цитирования.

## 12.3. Проверка фактических утверждений

Разбивать материал на проверяемые утверждения.

Классифицировать каждое утверждение как:

- `supported`;
- `unsupported`;
- `contradicted`;
- `uncertain`.

Для автоматической проверки допустимо использовать отдельный NLI-модуль или LLM-проверяющий, но необходимо фиксировать тип проверяющего и учитывать его ошибки.

Автоматический вердикт LLM не равнозначен доказанному факту.

Для исследовательской оценки предусмотреть ручную экспертную разметку.

## 12.4. Отчёт о проверке

Формировать машиночитаемый и человекочитаемый отчёты:

- количество утверждений;
- количество подтверждённых утверждений;
- неподтверждённые утверждения;
- противоречия;
- ошибки ссылок;
- покрытие требований;
- пробелы в знаниях;
- итоговый статус.

Не заявлять абсолютное отсутствие галлюцинаций на основании одной автоматической проверки.

# 13. Экспорт результатов

Поддерживать:

- Markdown;
- JSON;
- HTML.

Для MVP эти три формата обязательны.

Предусмотреть последующее расширение до DOCX и PDF.

Каждый сгенерированный материал должен сопровождаться:

- идентификатором запуска;
- конфигурацией модели;
- версией корпуса;
- версией графа;
- ссылками на использованные источники;
- отчётом верификации.

# 15. Научно-экспериментальный модуль

Это обязательная часть системы, а не дополнительная функциональность.

## 15.1. Сравниваемые архитектуры

**A. Free LLM**

Генерация по теме и формальным инструкциям, без извлечения источников.

**B. Dense RAG**

Семантический поиск с передачей найденных фрагментов в LLM.

**C. Hybrid RAG**

Dense + BM25 с объединением результатов.

**D. Hybrid RAG + Graph**

Гибридный поиск, дополненный графом понятий.

**E. Proposed Architecture**

Гибридный поиск, граф понятий, формальный планировщик, критерий достаточности и независимая проверка.

Для чистого анализа влияния отдельных компонентов предусмотреть дополнительные ablation-конфигурации, в том числе вариант E без графа и вариант E без проверки достаточности.

## 15.2. Условия сопоставимости

Для сравнимых экспериментов фиксировать:

- одинаковый корпус;
- одинаковые версии документов;
- одинаковые запросы и темы;
- одинаковую LLM;
- одинаковую embedding-модель;
- параметры генерации;
- ограничение доступного контекста;
- версию поискового индекса;
- аппаратные ограничения;
- число повторений.

Методы, использующие источники, должны иметь сопоставимые бюджеты контекста.

Необходимо фиксировать фактическую длину промптов, а не только установленный максимальный лимит.

## 15.3. Метрики поиска

Реализовать:

- Recall@k;
- Precision@k;
- MRR;
- nDCG@k;
- latency p50/p95;
- время индексации;
- размер индекса;
- потребление RAM.

Оценка поискового качества требует эталонной разметки релевантных фрагментов.

## 15.4. Метрики генерации

Реализовать:

- покрытие требований РП;
- покрытие обязательных понятий;
- долю фактических утверждений с подтверждёнными доказательствами;
- долю неподтверждённых утверждений;
- число противоречий;
- долю корректных ссылок;
- долю материалов, прошедших структурные проверки;
- экспертную оценку качества;
- время генерации;
- количество входных и выходных токенов;
- стоимость API, если применимо.

Метрики, зависящие от экспертной разметки, должны быть отделены от автоматических оценок.

## 15.5. Экспериментальный датасет

Предусмотреть создание:

- перечня учебных тем;
- набора поисковых запросов;
- эталонных релевантных фрагментов;
- эталонной структуры учебных материалов;
- набора проверяемых утверждений;
- экспертных оценок.

Датасет и правила его подготовки должны иметь версии.

Нельзя изменять тестовую разметку после просмотра результатов отдельного метода без фиксации новой версии набора.

## 15.6. Статистический анализ

Реализовать:

- сводные таблицы;
- распределения метрик;
- доверительные интервалы;
- парные сравнения на одинаковых заданиях;
- анализ ошибок;
- анализ зависимости качества от параметров;
- экспорт CSV и JSON;
- построение графиков.

Метод статистического сравнения выбирать с учётом типа данных, объёма выборки и характера повторных измерений.

Не объявлять улучшения статистически значимыми без соответствующего анализа.

# 17. Безопасность и эксплуатация

Обязательные требования:

- Не запускать прикладные процессы от root, если это не требуется.
- Не монтировать Docker socket в прикладные контейнеры.
- Не использовать привилегированные контейнеры.
- Не монтировать корневую файловую систему хоста.

- Не хранить секреты в репозитории.
- Не отправлять исходные образовательные документы во внешние API без явного разрешения.
- Проверять размеры и типы загружаемых файлов.
- Учитывать лицензионные ограничения учебников.

- Сохранять диагностические журналы без секретов и лишних персональных данных.

Для development-окружения допускаются более простые настройки, но это должно быть явно отражено в документации.

# 21. Критерии приёмки

Проект считается технически реализованным, если:

2. Для запуска не требуется установка прикладных Python-библиотек в хостовую ОС.

9. Генерация поддерживает минимум одного реального LLM-провайдера и mock-провайдер.
10. Проверка обнаруживает несуществующие и некорректные ссылки.
11. Система сохраняет параметры и результаты каждого эксперимента.
12. Реализованы все пять основных экспериментальных конфигураций.
13. Эксперимент можно повторить по сохранённой конфигурации.
14. Тесты выполняются из контейнерного окружения.
15. Документация позволяет развернуть систему без ручного изменения исходного кода.
16. Сервисы не публикуются во внешнюю сеть по умолчанию.

Научная гипотеза считается отдельно проверяемой. Успешное прохождение технических критериев не означает её подтверждения.
