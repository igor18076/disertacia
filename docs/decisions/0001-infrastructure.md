# ADR 0001. Переносимость и проверка инфраструктуры

**Статус** — принято для этапов 0–1.

## Условия

Разработчик редактирует код на Windows, а контейнеры работают на Debian Forky/Sid с CPU. Системный Python сервера и настройки уже работающих служб находятся вне проекта. Начальный запуск должен проверять зависимости до появления документов, коллекций и моделей.

## Решения

1. Использовать один Compose-файл для Linux-контейнеров. Образы идентифицируются версией и digest, зависимости Python фиксируются в `uv.lock`. Форматы файлов и относительные пути в Git одинаковы для Windows и Linux. [Использование uv в Docker](https://docs.astral.sh/uv/guides/integration/docker/)
2. Применять Alembic отдельным конечным процессом перед API. Начальная ревизия создаёт пространство имён `coursegen`. В случае ошибки команду и логи миграции можно проверить отдельно. Следующие этапы введут таблицы вместе с моделями данных.
3. Разделить две проверки. `/health` подтверждает, что API может обработать запрос. `/ready` выполняет SQL-запрос на доступ к схеме и запрашивает список коллекций через официальный клиент Qdrant. Пустая база коллекций допустима. При недоступности зависимости API возвращает HTTP 503 с именем сервиса. [Интерфейсы Qdrant](https://qdrant.tech/documentation/interfaces/)
4. Публиковать API только на loopback Debian. PostgreSQL и Qdrant доступны внутри сети Compose. Для удалённого клиента точкой входа служит SSH-туннель. Именованные тома позволяют пересоздавать контейнеры с сохранением баз.
5. Проверять обработку отказов в быстрых тестах. Отдельным запуском в Compose проверять сетевые адреса сервисов, PostgreSQL после миграции, SDK Qdrant и HTTP API. Критерий приёмки этапа 1 — успешный прогон с настоящими зависимостями на Debian.
6. Для сервера с ограниченным исходящим HTTPS поддерживать дополнительный режим сборки из перенесённых Linux wheels. Список зависимостей и допустимые хеши для обоих режимов определяет один `uv.lock`. Подготовленный архив хранится отдельно от Git.
